## 9. Should fix: the app cannot search by title, author, keyword or ISBN

**Category:** correctness (spec). **Confidence:** Confirmed.

**Location:**
- `app/lib/ui/results_page.dart:25` and `:56`
- `app/lib/ui/search_bar.dart:45`

**What is wrong:** the UI builds only `SearchQuery(q: …)`. A search across `lib/` finds no other
`SearchQuery` constructor and no `copyWith(title: / author: / keyword: / isbn:)`.

**How it fails:**
- spec.md asks for "title, author, and keyword searching", and says a known-item search shows "results only
  for that specific title".
- From the app, typing "Pride and Prejudice" sends `q=`, so `SearchQuery.is_known_item` is false and nothing
  is narrowed. The live `q=pride and prejudice` search returned 25 works, including "Pride and Prejudice and
  Zombies".
- The same title as `title=` with `author=Austen` returns 3 works.
- An ISBN typed into the box is sent as free text, never as `isbn=`.
- `_is_the_item`, `title_matches` and the study-aid rules are unreachable from the product.

**Suggested fix:** add a search-type control next to the box ("Anything / Title / Author / Subject / ISBN"),
or an "Advanced search" section with separate fields. Map each to the matching `SearchQuery` field. An
input that is a valid ISBN could also be sent as `isbn` automatically.

**Test that would have caught it:** in `search_results_test.dart`, choose "Title", type "Pride and
Prejudice", submit, and assert that `FakeSearchApi.lastQuery.title == 'Pride and Prejudice'` and that
`q` is null. Add one test per field.

**Status:** fixed 2026-10-11. The search box has a "Search in" choice (anything, title, author, subject, ISBN) and `SearchQuery.withTerm` sends one field; free text that is a valid ISBN goes as `isbn`. Tests in `search_results_test`, `models_test`, `isbn_test`.

## 10. Should fix: the text renderer flattens verse and drops text outside `<p>` and headings

**Category:** correctness, accessibility. **Confidence:** Confirmed for the line breaks; Plausible for the
dropped text.

**Location:** `app/lib/reader/content.dart:74` (`_clean`), `:84` (`'h1, h2, h3, h4, p'`).

**What is wrong:** `e.text` ignores `<br>`, and `_clean` folds every whitespace run into one space. Only
`h1`–`h4` and `p` are kept.

**How it fails:**
- The Raven (gutenberg.org/ebooks/1065.html.images) puts each stanza in one `<p>`, with a `<br>` after
  every line. In the reader, each stanza becomes one run-on line: "Once upon a midnight dreary, while I
  pondered, weak and weary, Over many a quaint…". Screen-reader users lose the verse structure too.
- By reading the selector, text that sits only in `div.poem`/`span` lines, `<pre>`, `<li>`, `<td>`,
  `<blockquote>` without a `<p>`, or `h5`/`h6` is dropped entirely.

**Suggested fix:**
- Turn `<br>` into `\n` before taking the text, and collapse spaces and tabs but not newlines.
- Walk block elements (`p`, `div`, `pre`, `li`, `blockquote`, `td`, `h1`–`h6`), taking the innermost blocks
  that hold text, rather than selecting a fixed list.
- Keep `\n` inside a paragraph in `BookText`. Today `split(' ')` would also lose it, so represent a line
  break as its own token.

**Tests:**
- `htmlParagraphs('<p>a<br>b</p>')` keeps the line break.
- `<div class="poem"><span>line</span></div>` is not dropped.
- `<pre>` text is kept.
- `<li>` text is kept.
- A rendering test showing two lines of one stanza on separate lines.

**Status:** fixed 2026-10-11. `htmlParagraphs` walks the block elements, keeps `<br>` and `<pre>` lines as `\n`, and keeps text in `li`, `td`, `div`, `h5`, `h6`. `BookText` makes the word after a break start with `\n`. Tests in `content_test`, `text_engine_test`.

## 11. Should fix: pagination freezes the UI for about a second on every relayout

**Category:** performance. **Confidence:** Confirmed (measured).

**Location:**
- `app/lib/reader/text_engine.dart:178-179`, which calls `_layoutPages` inside `build`
- `app/lib/reader/pagination.dart:44`

**What is wrong:** the whole book is paginated with `TextPainter`, synchronously, during a build.

**How it fails:**
- `paginate` on a 120,000-word book (about Pride and Prejudice's length: 1,906 pages at 360×600, 18 pt)
  took 1,285 ms, and 1,012 ms at width 361. That was on a desktop CPU in `flutter test`; phones are slower.
- It runs on first open, on every font, size or spacing change, on rotation, and on every frame of a window
  resize, because each new width is a new cache key.
- Text at 200% makes more pages and more work.
- Rotating a phone while reading should freeze for several seconds; I did not run it on a device.

**Suggested fix:**
- Paginate lazily: lay out the pages around `_anchor` at once, and compute the rest in slices with
  `SchedulerBinding.scheduleTask`, or a few pages per frame.
- Show "Page 12 of about 400" until the count is final.
- Debounce width changes during a resize.

**Test:** with a 120,000-word `longText`, assert that opening the book and changing the font size each
build their first frame in under, say, 100 ms (`tester.binding` frame timing, or a `Stopwatch` around
`pump`). Keep the threshold generous so the test isn't flaky.

**Status:** fixed 2026-10-11. `paginate` lays each paragraph out once (about 500 ms for 120,000 words, from 1,285 ms) and the engine runs it one 8 ms slice per frame. Meanwhile it shows the text from the reader's place (`reader-page-pending`) and "N% read". Not done: "Page 12 of about 400" and a debounce on window resizes (a resize starts a new count each time; an older one stops). Tests in `pagination_test`, `text_engine_test`.

## 12. Should fix: a failed or finished recording still shows "Pause", with no message

**Category:** failure handling, accessibility. **Confidence:** Confirmed by reading; not run on a device.

**Location:**
- `app/lib/ui/audio_player.dart:37-55`
- `app/lib/services/audio_engine.dart:17-25`

**What is wrong:**
- `togglePlay` and `playChapter` set `playing = true` before awaiting `_engine.play`. Nothing catches an
  error.
- Nothing listens to the player's state, so the end of a chapter is never noticed.

**How it fails:**
- archive.org is unreachable, or a LibriVox URL returns 404: `setUrl` throws a `PlayerException`, and the
  error goes unhandled from `onPressed`.
- The button stays "Pause", and screen readers announce the player as playing. No message tells the user
  what happened or what to do.
- When a chapter ends, the button also stays "Pause", and the next chapter does not start.
- `FakeAudioEngine.play` (`test/helpers/fakes.dart:207`) never fails and never completes, so no test can see
  either case.

**Suggested fix:**
- Wrap `play` in try/catch: on error, set `playing = false` and set an `error` message. Show the message in
  a `LiveRegion` with a retry.
- Expose a `playerStateStream` (or a completion stream) through `AudioEngine`. Use it to keep `playing` true
  only while just_audio plays, and to move to the next chapter.

**Tests:** let `FakeAudioEngine` fail the next `play` and emit "completed". Then assert that:
- after a failure, the button reads "Play" and an error live region appears;
- after "completed", chapter 2 starts.

**Status:** fixed 2026-10-11. `AudioEngine.play` throws `AudioException`; the controller shows `audio-error` with `audio-retry`, follows the player's `statusStream` (pause from outside, end of chapter) and starts the next chapter. Tests in `audio_player_test`.

## 16. Should fix: LibriVox: stripping "Il" and "De" loses real titles

**Category:** correctness. **Confidence:** Confirmed (live LibriVox API, 2026-10-11).

**Location:** `backend/app/sources/librivox.py:19-21` (`_LEADING_ARTICLE`).

**What is wrong:** LibriVox drops some leading articles from the titles it stores, but not these:

| Sent | LibriVox answer |
|---|---|
| `^Il Principe` | "Il Principe" |
| `^Principe` | not found |
| `^De Profundis` | "De Profundis", "De Profundis (version 2)" |
| `^Profundis` | not found |
| `^De Rerum` | "De Rerum Natura" |
| `^De Bello` | "De Bello Gallico Libri Septem" |

Dutch "De" is dropped, though: `^Kleine Johannes` finds "Kleine Johannes" and `^De Kleine Johannes`
does not. German "Die" is dropped too: `^Leiden des` finds "Leiden des jungen Werther".

**How it fails:** `title=De Profundis` gets nothing from LibriVox. The live search returned Gutenberg and
Open Library works only (LibriVox also timed out on that run). The same happens for Machiavelli's "Il
Principe" and Lucretius.

**Suggested fix:**
- Remove `il` from the list.
- `de` is ambiguous (Latin titles keep it, Dutch drop it). Send the title unstripped when it starts with
  "de", or retry once unstripped when the stripped search answers "could not be found". Given LibriVox's
  ~10 s latency, the first option is cheaper.
- Record the live results in api_librivox.documentation.md.

**Test:** in `test_source_librivox.py`, check that "Il Principe" sends `title=^Il Principe` and "De
Profundis" sends `title=^De Profundis`. Keep the existing cases for "Les Misérables" → `^Misérables` and
"Die Leiden…" → `^Leiden…`.

**Status:** fixed 2026-10-11. "Il" and "De" are no longer stripped; Dutch "De Kleine Johannes" is the known cost. Recorded in `api_librivox.documentation.md`. Tests in `test_source_librivox`.

## 17. Should fix: manifest building ignores the zip-entry size limit

**Category:** security. **Confidence:** Confirmed (reproduced).

**Location:** `backend/app/publications.py:64`, `:69`, `:115`, `:124` (`archive.read(...)`).

**What is wrong:**
- `max_entry_bytes` is checked only in `resource()`.
- `build_manifest` reads `container.xml`, the OPF and the nav/NCX with `archive.read`, which has no size
  limit.
- `backend/tests/README.md` says zip entries over 100 MB are refused "checked before and while reading,
  against zip bombs".

**How it fails:** I served a 149 KB EPUB whose OPF holds 150 MB of whitespace to a
`PublicationStore(max_entry_bytes=1000)`. The manifest was built anyway, and the whole entry was
decompressed into memory before parsing. Only gutenberg.org (or the configured mirror) is fetched, so
this needs a bad or compromised upstream. That is why it is not a blocker.

**Suggested fix:** one helper, `_read_entry(archive, name, limit)`, that checks `getinfo().file_size` and
reads at most `limit + 1` bytes. Use it everywhere, and give the package files a smaller limit (a few MB).

**Test:** in `test_publications.py`, an EPUB whose OPF is larger than `max_entry_bytes` gives
`PublicationUnavailable` (502) and is not cached.

**Status:** fixed 2026-10-11. `_read_entry` checks the listed size and reads at most `limit + 1` bytes; package files get min(`max_entry_bytes`, 5 MB). Tests in `test_publications` (container, OPF, nav, NCX; not cached).

## 18. Consider: a new recording can start at the previous recording's position

**Category:** correctness, tests. **Confidence:** Plausible.

**Location:**
- `app/lib/ui/audio_player.dart:12-15`, `:45`
- `app/lib/services/audio_engine.dart`

**What is wrong:**
- One `JustAudioEngine` is shared by the whole app.
- Each `AudioController` copies every `positionStream` value into `position`, whichever recording it belongs
  to.
- `togglePlay` then sends that position as `from:`.

**How it fails:**
- Listen to recording A to 20:00, then go back, which pauses A.
- Open recording B (another work) and press Play.
- In just_audio 0.10.6, a new `positionStream` listener gets the player's current position from the
  `playerEventStream`, so B's controller holds 20:00. B is then loaded with `setUrl(B, initialPosition:
  20:00)`.
- The slider on B's page also shows A's position before Play is pressed.
- `FakeAudioEngine.positionStream` is a plain broadcast stream that replays nothing, so the tests cannot
  show this.

**Suggested fix:** have the engine report the URL a position belongs to (for example
`Stream<(Uri, Duration)>`). The controller ignores positions for other URLs. Or the controller passes
`from: null` the first time it plays a URL it hasn't loaded.

**Test:** make `FakeAudioEngine` replay its last position to new listeners, as just_audio does. Then:
play A, seek to 20:00, close it, open B, press Play, and assert that `play` was called with `from == null`.

**Status:** fixed 2026-10-11 (with #12). Positions carry their file (`AudioPosition`); a controller ignores other files' positions. `FakeAudioEngine` replays its last position to new listeners. Tests in `audio_player_test`.

## 19. Consider: any book id makes the backend call gutenberg.org; per-id locks are never freed

**Category:** security, performance. **Confidence:** Confirmed.

**Location:** `backend/app/publications.py:226-228`, `:252`.

**What is wrong:**
- Any id from 1 to 99,999,999 triggers a download attempt. A 404 is not remembered.
- `_book_locks` gets one entry per id ever asked for, and entries are never removed.

**How it fails:**
- `/publications/gutenberg/99999999/manifest.json` answered 404 after 0.18 s, spent on a request to
  gutenberg.org.
- A script walking ids makes our server crawl Project Gutenberg, which blocks aggressive clients. That
  would break web reading for every user.
- Each walked id also leaves a `Lock` in memory.

**Suggested fix:**
- Before downloading, ask the local Gutendex whether the id exists and has an `application/epub+zip`
  format. This costs no external traffic.
- And/or cache 404s for a day.
- Replace the per-id dict with a fixed set of locks (`locks[id % 64]`).

**Test:** with a Gutendex fake that does not know id 5, `manifest(5)` raises `PublicationNotFound` and
makes no Gutenberg request. Separately, two requests for an unknown id make one upstream request.

**Status:** fixed 2026-10-11. The store asks the local Gutendex first (`GutendexCatalog`) and refuses unknown ids with no Gutenberg request; Gutendex down means "unknown" and books open as before. Locks are a fixed 64. Not done: caching 404s (unneeded now that unknown ids cost nothing external). Tests in `test_publications` (`TestUnknownBooks`, `TestGutendexCatalog`); checked live against the local Gutendex (1342 yes, 99999999 no, a dead URL unknown).

## 20. Consider: the 15 s source deadline uses the whole 15 s budget

**Category:** performance (spec). **Confidence:** Confirmed (measured).

**Location:**
- `backend/app/search.py:70`
- `backend/app/config.py:45`, `:95`

**What is wrong:** the time `wait()` allows for sources (`search_timeout_seconds = 15`) is the whole time
the spec allows for results. Merging, serialization, the network and rendering all come after it.

**How it fails:** every live search where LibriVox was slow took 15.02–15.10 s at the server, before any
network time. The app's own timeout is 20 s, so the user waits more than 15 s.

**Suggested fix:**
- Add a `FBR_SOURCE_DEADLINE_SECONDS` setting, defaulting to about 12. Keep the httpx timeout at or below
  it.
- Update the README's "15 s" wording. This is separate from the open LibriVox decision in spec.md's Risks.

**Test:** `test_default_timeout_*` asserts the deadline is below 15 s. A slow `FakeSource` search returns
in under 15 s, measured.

**Status:** fixed 2026-10-11 (simple version). `search_timeout_seconds` now defaults to 12 and is both the wait for sources and the HTTP timeout, so no new setting was added (`FBR_SEARCH_TIMEOUT_SECONDS` already sets it). Progressive results were considered and not built. Test: `test_default_timeout_leaves_room_inside_the_15_second_budget`.

## 21. Consider: the known-item author filter keeps "Jr." for the father, and "(anon)" keeps everyone

**Category:** correctness. **Confidence:** Confirmed (run).

**Location:** `backend/app/search.py:115-118`.

**What is wrong:** the filter accepts a book when the query's name parts are a subset of the author's.

**How it fails:**
- `_is_the_item(book by "Charles Dickens Jr.", author="Charles Dickens")` is `True`, so the son's books
  pass a search for the father. (Review #8 noted the reverse case works.)
- `author="(anon)"` normalizes to an empty set, which is a subset of everything. The author filter is
  then off, and every book with any author passes.
- The subset rule itself is reasonable: "Mary Shelley" should find "Mary Wollstonecraft Shelley".

**Suggested fix:**
- Treat a trailing suffix on the book's author as significant: if the book has "Jr." and the query does
  not, it is not a match.
- Treat an author query with no name left as no match, or reject it with 422, as LibriVox already makes no
  request for it.

**Test:** two `TestKnownItemSearch` cases, one for each.

**Status:** fixed 2026-10-11 for "(anon)": a name with nothing left matches no book. The "Jr." half was not kept: by user decision a search for "Charles Dickens" also returns "Charles Dickens Jr." Tests in `test_search_service`. The per-book recomputation of `author_key` is not changed.

## 24. Consider: slow searches can use up FastAPI's thread pool, so book files wait

**Category:** performance. **Confidence:** Plausible (not load-tested).

**Location:** `backend/app/main.py:45-65`.

**What is wrong:** `/search` is a sync endpoint, so each request holds one of anyio's 40 worker threads
for up to 15 s. That is every search while LibriVox is slow. `/publications/...` and `/health` use the same
pool.

**How it fails:** at about 3 searches a second, all 40 threads are waiting. Web readers then stall on every
chapter file, and `/health` stops answering. Use is expected to be low, so this is a "consider".

**Suggested fix:**
- Make `/search` `async`, and run `search_service.search` with `anyio.to_thread.run_sync` on its own
  `CapacityLimiter`. Then searches cannot use up the threads that book files need.
- Or raise the default limiter, and document the limit.

**Test:** a test with a slow `FakeSource` and 40 concurrent searches checks that a `/publications`
request still answers quickly.

**Status:** fixed 2026-10-11. `/search` is `async` and runs on its own `CapacityLimiter` (`FBR_MAX_CONCURRENT_SEARCHES`, default 20). Tests in `test_api` (`TestSlowSearchesDoNotStarveTheRest`: `/health` answers with 50 searches waiting; no more than the limit run at once). Not load-tested with real sources.

## Readability and efficiency notes

- **`backend/app/merge.py`:**
  - `_same_authors` pairs authors by sorted surname. In a multi-author book, a misspelled surname can shift
    the pairing ("Mary Shelley"/"Mary Shelly" next to "Percy Bysshe Shelley") and miss a merge. It never
    causes a false merge. Matching each author to any unused partner would fix it.
  - `_work` de-duplicates identifiers with `v not in bucket` on a list. That is quadratic for Open
    Library's 3,714-ISBN works. Keep a `set` beside the list.
- **`backend/app/search.py`:** `_is_the_item` recomputes `author_key(query.author)` and
  `normalize_isbn(query.isbn)` for every book. Compute them once per search.
- **`backend/app/publications.py`:**
  - `_fetch` raises `KeyError` (a 500) on a redirect without `Location`.
  - A missing nav/NCX file fails the whole book. Dropping the table of contents would be kinder.
  - `.part` files left by a crash are never cleaned up, and the cache size doesn't count them.
- **`backend/app/sources/openlibrary.py`:**
  - `availability()` is used only by tests. Remove it, or mark it as kept for later.
  - Titles keep trailing spaces ("Pride and Prejudice "). Strip them in `_book`.
- **`app/lib/reader/reader_page.dart`:** a Readium bookmark saved before the first locator event is saved
  as progress 0 with no locator. Disable the bookmark button until `positions` has emitted once.
- **`app/lib/ui/results_page.dart`:** there is no way to ask for page 2; the app always sends `page=1`. The
  results are built in a `Column`, which is fine at about 85 rows. Revisit both together if paging is added.
- **`backend/requirements-dev.txt`:** the one test warning asks for `httpx2` with Starlette's TestClient.
  Pin or upgrade before it becomes an error.

## Habit to build

Finish each feature at the user's screen, not at the API. #9, #13 and #14 all come from the same gap: the
backend contract is well tested, but nobody followed it to the button a user presses and the words they
read. #18 is the same gap one level down: the fake engine was simpler than the real player. When a backend
capability lands, add one app test that reaches it through the UI. When you write a fake, copy the real
dependency's awkward behaviour (replaying the last value, failing, completing), because those are the cases
the fake exists to test.
